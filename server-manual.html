1. Overview

Sysible Server is a Debian-stable server image with the toolchain for running server software already installed. No desktop, no display manager, no GUI applications: it boots to a console and is reached over SSH.

It is not a fork. The base is Debian stable, the package manager is apt, and every Debian package you know is still there under its usual name. What the image adds is the set of things a container and automation host needs before it is useful — and a small number of Sysible programs that install and check the rest.

Two things make it different from a Debian netinst you install yourself:

Debian netinstSysible Server
Container runtimeyou add Docker's repository, key and packagesdocker-ce, docker-compose-plugin and containerd.io are hard dependencies of the image
Automationyou install Ansible, OpenTofu, kubectl, Helminstalled, with the third-party repositories already trusted
Firewallnone configurednftables installed, fail2ban and auditd running
Sysible appsnot availableasked for during the install, set up on first boot

The image ships for amd64 and arm64. Both are built from the same tree in the same release, with the same package set.

Everything in this guide is in the image. Nothing here needs a subscription, a licence server or an account. The release key that signs the downloads is published at sysible.com/security.

Installing the Sysible apps needs working DNS and outbound HTTPS to GitHub and Docker Hub. The base install does not — you can install offline and set the apps up later.

4. Getting the ISO

Each release publishes both architectures. The ISO is larger than GitHub's 2 GB per-file limit, so it ships as numbered .part files with checksums for the parts and for the reassembled image.

Download, for your architecture, every sysible-server-<arch>.iso.*.part plus SHA256SUMS.<arch>.parts, SHA256SUMS.<arch>.parts.gpg, SHA256SUMS.<arch> and SHA256SUMS.<arch>.gpg.

gpg --verify SHA256SUMS.<arch>.parts.gpg SHA256SUMS.<arch>.parts
sha256sum -c SHA256SUMS.<arch>.parts
cat sysible-server-<arch>.iso.*.part > sysible-server-<arch>.iso
gpg --verify SHA256SUMS.<arch>.gpg SHA256SUMS.<arch>
sha256sum -c SHA256SUMS.<arch>

There are two signatures because there are two things to check: the parts you downloaded, and the image you assembled from them. Checking only one leaves the other unverified.

Import the Sysible release key and confirm its fingerprint out of band before you trust either signature. A key fetched from the same place as the file proves nothing. The fingerprint is published at sysible.com/security.

5. Writing the installer medium

Write the reassembled .iso to a USB stick with dd, balenaEtcher or Rufus.

sudo dd if=sysible-server-amd64.iso of=/dev/sdX bs=4M status=progress conv=fsync
of=/dev/sdX is the device, not a partition — /dev/sdb, not /dev/sdb1. Writing to the wrong device destroys it. Confirm with lsblk first.

In a hypervisor, attach the ISO and choose Debian 12.x (64-bit) as the guest type — 64-bit ARM on Apple Silicon. Give it 4 GB of RAM and 40 GB of disk, and enable nested virtualization if you intend to run containers or VMs inside it.

6. Installing

Boot the medium. The Sysible boot menu appears; choose the install entry.

The installer is the Debian Installer, with Sysible's banner and palette. It asks the usual questions — language, keyboard, hostname, domain, users and passwords, clock, partitioning — and two of its own.

Optional software to install

A checklist of separately licensed tools: terraform, vault, consul, nomad, packer, boundary, aws-cli. The HashiCorp tools are BUSL-1.1 licensed and not open source; ticking them means you accept that licence. Nothing is installed during the install itself — the selection is recorded and acted on at first boot.

Sysible software to set up on first boot

A checklist of the platform itself:

TickWhat you get
slopThe Controller, SLEP and Connect behind one front door at https://slop.lan/ with a single sign-in. Recommended; it already covers all three
controllerSysible Controller — the fleet console
slepSysible Linux Engineering Platform — Terraform, Ansible and Salt
connectSysible Connect — a terminal in the browser

Tick nothing to set nothing up. Anything chosen here can be changed afterwards with sudo install-sysible.

Both answers are recorded into the installed system and acted on by a systemd unit at first boot — not during the install. The installer has no guaranteed network, and an offline install has none at all, so the work waits for a boot that does.

Partitioning, bootloader installation and reboot proceed as in any Debian install. The image writes its bootloader for both UEFI and BIOS.

7. First boot

The machine boots to a console and prints a login prompt. Two one-shot services run in the background once the network is up.

UnitWhat it does
sysible-tools-firstboot.serviceInstalls the optional tools you ticked, then removes its request file
sysible-apps-firstboot.serviceInstalls the Sysible apps you ticked, through install-sysible
sysible-regenerate-ssh-host-keys.serviceGenerates this machine's own SSH host keys

Both read their request from /etc/sysible/, wait for network-online.target, and have no start timeout — cloning repositories and building containers takes far longer than systemd's default.

They behave differently on failure, deliberately:

  • Tools. The request is consumed whether or not the install worked, so a failed download does not retry on every boot. Re-run it yourself with sudo sysible-tools install <tool>.
  • Apps. The request is kept and retried on the next boot, up to three attempts. After that it gives up and writes /etc/sysible/apps-failed, which the login hint reads out so the failure is visible rather than silent.

Watch either from the console:

journalctl -u sysible-apps-firstboot -f
tail -f /var/log/sysible-apps-firstboot.log
tail -f /var/log/sysible-tools-firstboot.log
Nothing listens on the network until the apps finish installing. A port that is not open yet on a freshly installed machine is usually this, not a fault.

8. Accounts and SSH

The installer creates your account; no default login ships in the installed system. sudo is installed and the account you create during the install is given administrative rights.

Password quality is enforced by libpam-pwquality, with the policy in /etc/security/pwquality.conf.d/. It is a hard dependency so it cannot be silently dropped.

SSH is enabled and hardened. Host keys are regenerated on first boot, so two machines installed from the same image do not share an identity.

ssh-copy-id you@server
ssh you@server
Set up key authentication and then disable password authentication in /etc/ssh/sshd_config.d/. fail2ban throttles brute force, but a key removes the attack rather than slowing it.

9. The Sysible apps

install-sysible installs the platform. It is the same program on Sysible Server and Sysible Workstation — byte-identical, with the edition read from /etc/os-release at run time.

sudo install-sysible                    # a menu, everything ticked
sudo install-sysible slop               # all three apps behind the gateway
sudo install-sysible controller slep    # just those two
sudo install-sysible --uninstall        # remove them
sudo install-sysible --reinstall slop   # remove, then install cleanly
ArgumentMeaning
controllerSysible Controller, on its own address
slepSysible Linux Engineering Platform
connectSysible Connect
allAll three, each on its own address, no gateway
slopAll three behind the SLOP gateway at https://slop.lan/

Each product is cloned to /opt/sysible-src/<repo> and brought up as a container through sysiblectl, which is installed too, so you manage everything afterwards from one command.

slop supersedes the rest. The gateway only makes sense in front of the apps, so selecting it installs all three regardless of what else was chosen.

Point slop.lan and the controller., slep. and connect. subdomains at the host — in DNS, or in the client's /etc/hosts — to reach the gateway by name.

10. Optional tools

sysible-tools installs the separately licensed tools on demand, after the install.

sysible-tools                        # interactive menu
sysible-tools list                   # the catalogue and what is installed
sudo sysible-tools install vault consul

The catalogue is terraform, vault, consul, nomad, packer, boundary and aws-cli.

Terraform, Vault, Consul, Nomad, Packer and Boundary are licensed under the BUSL-1.1 and are not open source. Installing them means accepting HashiCorp's licence. OpenTofu — the open Terraform drop-in — is already in the image and needs no acceptance.

12. Updates

The image is Debian stable, so apt works exactly as it does anywhere else.

sudo apt update && sudo apt upgrade

Security updates install automatically through unattended-upgrades. Sysible's own packages come from the Sysible apt repository, configured by sysible-release and pinned to the sysible-stable suite.

Each build publishes a uniquely versioned package at a unique pool path, so a rebuild never rewrites a file a CDN has been told to cache — the cause of File has unexpected size errors on repositories that reuse paths.

sysible-release-check.timer checks periodically whether a newer Sysible release exists and records the answer; it does not install anything.

The Sysible apps are not apt packages. Update them with sysiblectl update all.

13. Containers

Docker Engine, the Compose plugin and containerd are installed and running. Your account is not in the docker group by default — being in it is equivalent to root.

sudo usermod -aG docker "$USER"   # then log out and back in
Adding a user to the docker group grants root-equivalent access to the host. On a multi-user machine prefer sudo docker, or use podman, which runs rootless.

14. Firewall and hardening

nftables is installed as a hard dependency and is what sysible verify looks for. It ships without a restrictive policy — the image does not guess which ports you need.

sudo nft list ruleset

Also present and running: fail2ban (SSH brute-force throttling), auditd (audit log), apparmor (mandatory access control profiles) and lynis (an on-demand audit tool, run with sudo lynis audit system).

15. Virtualization

libvirt-daemon-system, qemu-system and qemu-utils are installed, headless. sysible verify --virtualization reports whether KVM is actually usable — on a VM that normally means nested virtualization is off in the hypervisor.

sudo usermod -aG libvirt "$USER"
virsh list --all

16. Branding guard

What the boot menu calls this machine lives in one file that belongs to the image rather than to a package, so no upgrade ever restores it. A machine installed while that file was wrong would have kept booting a menu naming the wrong product forever.

sysible-branding-guard.service corrects the GRUB distributor at boot and regenerates the menu if it had to change anything. It leaves a distributor that is not Sysible's alone.

17. Troubleshooting

The apps never came up. Check the first-boot log. The usual cause is DNS or no route to Docker Hub.

systemctl status sysible-apps-firstboot
cat /var/log/sysible-apps-firstboot.log
cat /etc/sysible/apps-failed      # exists only if it gave up
sudo install-sysible slop         # run it yourself

A tool I ticked is missing. The tools request is consumed on first boot even if the download failed. Install it directly:

sudo sysible-tools install terraform

apt upgrade reports File has unexpected size. A stale cache. Clear it and retry:

sudo rm -rf /var/lib/apt/lists/*
sudo apt update

sysible verify says no firewall configured. nftables is installed but has no ruleset loaded. Load one, or ignore the check — it is non-critical.

The console shows a pending-setup hint at every login. The apps request is still outstanding. Either let the next boot retry it, or run install-sysible yourself and the hint clears.

18. Security model

  • The image is signed. Checksums for the parts and for the reassembled ISO are GPG-signed with the Sysible release key (ed25519). Verify both.
  • No default login survives the install. The live session's credentials do not reach the installed system; the installer creates your account.
  • Host keys are per machine. Regenerated on first boot, so cloning an image does not clone an SSH identity.
  • Password quality is enforced by PAM, as a hard dependency.
  • Nothing listens until you ask it to. The base image runs no Sysible services and opens no ports. The apps are installed only if you chose them.
  • The apps are built from source on your host — cloned from their official repositories, not pulled as opaque images from a Sysible registry.
  • Third-party repositories are pinned by key. Docker's apt repository is configured at build time with a fingerprint-checked key.
sysible verify reports posture; it does not harden the machine for you. A firewall policy, SSH key-only authentication and your own patch cadence are still yours to set.
