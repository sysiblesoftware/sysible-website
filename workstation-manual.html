1. Overview

Sysible Workstation is a Debian-stable desktop for people who build and run Linux infrastructure. It is a live image: boot it and you are in a working GNOME session with the whole toolchain present, before installing anything.

It is the same base and the same toolchain as Sysible Server, with a desktop on top. If you have read that guide, most of this one will be familiar — the package set, install-sysible, sysible-tools and sysible verify behave identically, because they are the same programs.

What the desktop adds:

SessionGNOME, on Wayland where the hardware allows
EditorVSCodium — Visual Studio Code without Microsoft's telemetry or branding
TerminalSysTerm, the Sysible terminal
Virtualizationvirt-manager and virt-viewer over libvirt/QEMU
CaptureWireshark, with the capture group already set up
OfficeLibreOffice Writer, Calc and Impress
Guest integrationopen-vm-tools, spice-vdagent and qemu-guest-agent, so it behaves properly inside a hypervisor

The image ships for amd64 and arm64 — Intel and AMD machines, and Apple Silicon under a hypervisor.

The live session is fully functional. You can evaluate the entire toolchain, including Docker and the Sysible apps, without writing anything to disk.

4. Getting the ISO

Each release publishes both architectures. The ISO exceeds GitHub's 2 GB per-file limit, so it ships as numbered .part files with checksums for the parts and for the reassembled image.

gpg --verify SHA256SUMS.<arch>.parts.gpg SHA256SUMS.<arch>.parts
sha256sum -c SHA256SUMS.<arch>.parts
cat sysible-workstation-<arch>.iso.*.part > sysible-workstation-<arch>.iso
gpg --verify SHA256SUMS.<arch>.gpg SHA256SUMS.<arch>
sha256sum -c SHA256SUMS.<arch>

There are two signatures because there are two things to verify: the parts you downloaded, and the image you assembled.

Confirm the Sysible release key's fingerprint out of band before trusting either signature — it is published at sysible.com/security. A key fetched from the same place as the file proves nothing.

5. Writing the installer medium

sudo dd if=sysible-workstation-amd64.iso of=/dev/sdX bs=4M status=progress conv=fsync
of= takes the device (/dev/sdb), not a partition (/dev/sdb1). Check with lsblk first; writing to the wrong device destroys it.

balenaEtcher and Rufus work too. The image is isohybrid, so one file boots on UEFI and BIOS alike.

In VMware Fusion, VirtualBox or UTM

Attach the ISO and choose Debian 12.x (64-bit) as the guest type — 64-bit ARM on Apple Silicon. open-vm-tools and spice-vdagent are preinstalled, so clipboard sharing and display auto-resize work without installing guest additions.

6. The live session

Pick Sysible Workstation (Live) from the boot menu. GNOME starts and signs in automatically.

There is no password. The live account, sysible, ships with no password hash and is then locked, so no credential is baked into the image and none can leak from it. Sign-in happens through GDM's autologin, which needs no password at all. sudo works without one in the live session.

The live session writes to RAM. Anything you create is gone at shutdown unless you save it elsewhere.

7. Installing to disk

Launch Install Sysible Workstation. Calamares asks for location, keyboard, partitioning, and your account.

Partitioning offers erase-disk, install alongside an existing system, or manual partitioning. The bootloader is written for UEFI and BIOS.

What happens to the live account

You create your own account during the install, and Calamares sets root's password. Once your account exists, the live sysible account is removed from the installed system, so an installed machine never carries a leftover default login.

If you name your own account sysible, it is kept — that account is now yours, with the password you chose.

Password quality is enforced by libpam-pwquality, a hard dependency, with the policy in /etc/security/pwquality.conf.d/.

8. The desktop

GNOME, with Sysible's artwork and GRUB theme. sysible-avatar.service seeds the Sysible avatar into AccountsService for human users, so the login screen looks like part of the product rather than a stock Debian install.

VSCodium is the editor — Visual Studio Code's source without Microsoft's telemetry or branding, so extensions come from Open VSX.

10. The Sysible apps

install-sysible installs the platform. It is byte-identical to the copy on Sysible Server — the edition name is read from /etc/os-release at run time, so the two cannot drift.

sudo install-sysible                    # a menu, everything ticked
sudo install-sysible slop               # all three apps behind the gateway
sudo install-sysible controller slep    # just those two
sudo install-sysible --uninstall
sudo install-sysible --reinstall slop
ArgumentMeaning
controllerSysible Controller, on its own address
slepSysible Linux Engineering Platform
connectSysible Connect
allAll three, each on its own address, no gateway
slopAll three behind the SLOP gateway at https://slop.lan/

On the desktop, Install Sysible Software runs the same thing with a checklist. Each product is cloned to /opt/sysible-src/<repo> and brought up as a container through sysiblectl.

slop supersedes the rest: the gateway only makes sense in front of the apps, so choosing it installs all three.

sysible-install is an alias for install-sysible — both spellings work and take the same arguments.

13. Updates

sudo apt update && sudo apt upgrade

Security updates install automatically via unattended-upgrades. Sysible's own packages come from the Sysible apt repository, configured by sysible-release and pinned to sysible-stable. Each build publishes a uniquely versioned package at a unique pool path, so a rebuild never rewrites a cached file.

sysible-release-check.timer records whether a newer release exists; it installs nothing.

The Sysible apps are not apt packages — update them with sysiblectl update all.

14. Containers

Docker Engine, the Compose plugin and containerd are installed and running. In the live session the sysible account is already in the docker group. On an installed system your own account is not:

sudo usermod -aG docker "$USER"   # then log out and back in
The docker group is root-equivalent. On a shared machine prefer sudo docker, or use podman, which runs rootless.

15. Virtualization

virt-manager and virt-viewer are installed over libvirt and QEMU. The live account is already in the libvirt and kvm groups; add your own account after installing:

sudo usermod -aG libvirt,kvm "$USER"
virsh list --all

sysible verify --virtualization reports whether KVM is actually usable. Inside a VM, "not usable" normally means nested virtualization is off in the hypervisor.

16. Enrolling with Sysible Controller

Enroll with Sysible Controller in the app grid registers this machine with a Controller so it appears in the fleet console and can be patched and managed from there. You need the Controller's address and an enrolment token from its Host enrollment page — see the Sysible Controller manual.

17. Branding guard

What the boot menu calls this machine is one line in a drop-in that belongs to the image, not to a package, so no upgrade ever restores it. sysible-branding-guard.service corrects the GRUB distributor at boot and regenerates the menu only if it had to change something. A distributor that is not Sysible's is left alone.

18. Troubleshooting

The live session boots to a black screen or a text console. A graphics driver problem. Switch to a VT with Ctrl+Alt+F3 and check systemctl status gdm3. In a VM, enable 3D acceleration or raise the video memory.

Clipboard or display resize does not work in a VM. The guest tools are installed but the matching host side may not be. On VMware install VMware Tools on the host side; on QEMU/SPICE make sure the SPICE agent channel is attached.

Docker says permission denied. Your account is not in the docker group on an installed system. Add it and log out and back in — a new group membership does not apply to an existing session.

sysible verify says no firewall configured. nftables is installed but no ruleset is loaded. The check is non-critical; load a policy if you want it to pass.

The installer will not let me use the whole disk. The live medium cannot repartition the device it booted from. Install from a USB stick to an internal disk, or from an ISO to a virtual disk.

I installed and the sysible account is gone. That is deliberate — see Installing to disk.

19. Security model

  • No default password anywhere. The live account ships with no password hash and locked; the live session signs in through GDM autologin, which needs none. root ships locked and is set by the installer.
  • No default login survives installation. Calamares removes the live account once your own exists.
  • The image is signed. Checksums for the parts and for the reassembled ISO are GPG-signed with the Sysible release key (ed25519). Verify both.
  • Host keys are per machine, regenerated on first boot, so cloning an image does not clone an SSH identity.
  • Password quality is enforced by PAM as a hard dependency.
  • Nothing listens until you ask it to. The base image runs no Sysible services and opens no ports.
  • The apps are built from source on your host, cloned from their official repositories — not pulled as opaque images from a Sysible registry.
  • Third-party repositories are pinned by key. Docker's apt repository is configured at build time with a fingerprint-checked key.
The live session has passwordless sudo. Anyone who can boot your USB stick has root on that session — and on any disk attached to the machine. Treat the medium as you would a root shell.
